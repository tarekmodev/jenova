01

What we're building & why it can win

eJuniper and TravZilla Pro sell the same fundamental thing: a booking engine platform that a travel company (tour operator, consolidator, DMC, OTA) licenses to run its business — one core engine for inventory, pricing, bookings, and finance, exposed through several sales channels and a back office.

Jenova is the same category of product, multi-tenant from day one, but organized the way Odoo organizes ERP: every tenant gets one Internal Dashboard for its staff, and capabilities arrive as installable apps — B2B (trade-partner distribution), Corporate (corporate clients as sub-tenants), Accounting & Finance, API Access, B2C Storefront, CRM, Omnichannel Support Desk, and Contracting (own inventory). Each app is an isolated module on the shared engine, each app is a pricing SKU, and a tenant enables only what its business needs.

Where the incumbents are weak

  • Legacy UX. Juniper and TravZilla interfaces are dense, slow, desktop-era. A modern, fast, mobile-usable agent portal is a genuine differentiator agents feel daily.
  • Arabic is an afterthought. RTL layouts, Arabic content, Hijri-aware date handling, and Saudi fiscal compliance (ZATCA e-invoicing) are bolt-ons for global vendors. For Jenova they are native.
  • Onboarding time and price. Incumbent implementations take months and five-to-six-figure setup fees. A self-service-leaning SaaS with tenant provisioning in days, at GCC-friendly pricing, attacks the long tail of small and mid-size agencies and operators the incumbents ignore.
  • AI-era operations. Being built by and around AI agents means Jenova can ship AI-assisted features incumbents can't retrofit quickly: natural-language search for agents, automated supplier reconciliation, disruption handling.
  • App-based packaging. Incumbents sell monolithic licenses with professional-services add-ons. Jenova's Odoo-style app model means a small agency starts with just B2B + Finance, adds Corporate when it lands its first company account — self-service expansion revenue instead of sales cycles.

The wedge: the best B2B hotel-booking experience in the GCC, live across all four channels, at a price and onboarding speed the incumbents can't match — then widen product coverage from that beachhead.

02

Scope, assumptions & the honest constraint

Decisions already made

  • The tenant experience is an Internal Dashboard with installable apps (Odoo model). The catalog: B2B, Corporate, Accounting & Finance, API Access, B2C Storefront, CRM, Omnichannel Support Desk, and Contracting — plus the core bookings workspace every tenant gets. Apps are built in the order §10 lays out, but they are all one product, not versions.
  • Corporate clients are sub-tenants: created and managed by tenant staff through the Corporate app, with their own portal, travel policies, approval workflows, and account billing.
  • Every tenant gets its own database as the standard architecture, with tiers above it: dedicated instance/region, then private-cloud or on-premise tenant deployment as an enterprise tier after GA. Sub-tenants get a synced Data Vault (their data replicated to a database they host, cloud or on-prem) rather than fragmenting their tenant's operational database (§3).
  • Per-sub-tenant customization happens through an extensibility framework — custom fields, webhooks, connector catalog for CRM/ERP/finance/HRM systems — never per-customer code forks (§5.9).
  • All product verticals are in scope: hotels, flights, transfers & activities, dynamic packages.
  • Inventory comes from supplier aggregator APIs at launch; tenants' own contracted inventory arrives with the Contracting app late in the build order, entering search as an internal adapter.
  • Saudi Arabia / GCC is the launch market: Arabic + English, RTL-first UI, SAR base currency with full multi-currency, mada payments, ZATCA compliance.
  • Build capacity is one technical director orchestrating Claude Code agents.
The honest constraint

The full catalog — eight apps, four product verticals — exceeds the Juniper feature matrix, historically 20+ engineer-years. It is achievable solo-with-agents only if two disciplines hold: (1) apps and portals are thin skins over one engine — the Corporate Portal, B2C site, and Partner API must reuse the exact same search/book/ledger services as the B2B app, never parallel implementations; (2) everything ships as one product but is built in strict order — revenue-gating apps first (hotels through B2B by month 5, when the platform starts earning), then Corporate, then more products, with CRM, Support Desk, and Contracting closing the catalog. The milestone plan in §10 encodes this order; a milestone never starts before the previous one's gate passes.

Explicitly out of scope

  • Raw GDS integration (Amadeus/Sabre terminals, ticketing plates) — flights go through a consolidator API that handles ticketing.
  • Cruise, rail, insurance verticals.
  • Native mobile apps — all portals are responsive PWAs.
  • Marketplace payments / split settlement — tenants settle with suppliers and agents through the credit ledger and their own gateway accounts.
03

System architecture

A modular monolith with asynchronous workers — not microservices. One deployable API process with strictly enforced internal module boundaries (a dependency-lint rule per module), one worker process for queues, one Postgres. This is deliberate: a solo director cannot operate twelve services, and module boundaries in a monorepo give agents the same isolation microservices would, without the distributed-systems tax. Any module can be extracted later because boundaries are real from day one.

How everything works through the apps

Cross-cutting rules

  • Tenancy: one database per tenant. Every tenant gets its own Postgres database at provisioning; the gateway resolves tenant → connection on every request, so a cross-tenant query is not merely forbidden but impossible. A small control-plane database holds platform-level data (tenants, app entitlements, platform billing, platform users), and Platform Admin fans out across tenant databases for cross-tenant views. Migrations run against every tenant database automatically in CI/CD — written that way from the first migration.
  • Apps and portals call services, never tables. The B2C site, Corporate portal, and Partner API all book through the identical BookingService the Agent Portal uses; differences (who pays, which markup or policy applies) are parameters, not forks.
  • Apps are entitlements, not codebases. An app = a NestJS module + dashboard section + portal (where applicable) + a feature flag on the tenant. Installing an app flips the entitlement and seeds its default data; nothing is deployed per tenant.
  • Everything supplier-facing is async-tolerant. Supplier calls run with budgets and circuit breakers; bookings that suppliers confirm late move through pending_confirmation states rather than blocking requests.
  • Money is integers. Minor units + currency code everywhere; conversion happens only at display time and at ledger-posting time with a stored rate.

Data isolation & deployment tiers

Database-per-tenant is the base architecture; the tiers differ only in where that database lives — Jenova's cluster, a dedicated instance, or the tenant's own infrastructure. The data-access layer resolves a tenant to a connection at request time, so every tier runs the same code, and migrations fan out across all tenant databases automatically.

Why sub-tenants don't get operational databases

A sub-tenant's bookings are the tenant's ledger, credit checks, and reports — splitting them into per-sub-tenant databases would turn every statement and search into a cross-database query and multiply migrations by thousands. The Data Vault delivers what sub-tenants actually need — their data, in their infrastructure, in real time — without fracturing the core.

05

Module specifications

5.1 Supplier integration layer

One TypeScript interface per vertical (HotelSupplierAdapter, FlightSupplierAdapter, GroundSupplierAdapter) with the same lifecycle: search → check (revalidate price/availability) → book → retrieve → cancel. Each adapter is an isolated package with its own contract-test suite recorded against the supplier's sandbox. This is the most agent-friendly part of the codebase: once the first adapter proves the contract, each new supplier is a self-contained, parallelizable task.

  • Normalization is the adapter's whole job. No supplier's shapes ever cross the adapter boundary: every response — whatever its structure — is translated into the canonical domain models (Offer, RatePlan, CancellationPolicy, BookingItem) before the engine sees it. That means normalizing the parts suppliers disagree on most: money (currency, minor units, tax inclusion), dates and timezones, occupancy/pax encodings, room- and board-basis codes, cancellation-policy deadline formats, amendment rules, and a unified error taxonomy (sold-out vs. price-changed vs. supplier-timeout vs. rejected). The engine, pricing rules, and every app work only with canonical types — a new supplier never touches them.
  • Wire-format agnostic: suppliers speak JSON REST, XML, or SOAP — the adapter contract doesn't care. The supplier-sdk ships shared transport codecs (HTTP client with retries/circuit breakers, JSON serializer, XML/SOAP builder-parser with schema validation) so an XML supplier's adapter differs from a JSON one only in its mapping code, and the record-and-replay harness captures both formats identically.
  • Certification kit per supplier: a checklist + automated test-run report, since every aggregator requires certification before production credentials.
  • Sandbox-first, no fabricated data: development runs against live supplier sandboxes with real test credentials from day one, so the engine is shaped by real supplier behavior — their response formats, cancellation-policy encodings, and error codes — not by assumptions. For CI and load tests, a record-and-replay harness captures real sandbox traffic and replays it deterministically: every byte originated from the supplier, nothing is invented, and automated runs don't burn sandbox quotas or flake on supplier downtime.
  • Hotel mapping: start with a licensed mapping service (Vervotech or GIATA) rather than building dedup — it's a multi-year problem. Budgeted in §12.

5.2 Search & availability

Fan-out orchestrator: a search hits every enabled supplier account for the tenant in parallel with a hard time budget (~8s hotels), streams results as suppliers respond (server-sent events to the portals), dedupes via canonical mapping, and picks cheapest-per-room-basis with alternatives retained. Static content cached aggressively; availability cached seconds-to-minutes keyed by (supplier, hotel, dates, occupancy, nationality) — nationality matters because GCC rates vary by it. A mandatory check step revalidates price before payment; price-change deltas surface to the buyer for re-approval.

5.3 Pricing & markup engine

Pure function: (net rate, context) → sell price + breakdown. Context = tenant, channel, agency, product, supplier, destination, travel dates. Rules resolve most-specific-wins with an audit trail of which rule fired stored on the Offer. Handles markup, agency discount, agent commission, VAT treatment, and rate-of-exchange with a tenant-configurable buffer. Fully unit-testable — one of the first modules agents build, with a property-based test suite.

5.4 Booking engine

Each BookingItem runs an explicit state machine (quoted → reserved → confirmed → issued → completed, with pending_confirmation, cancelled, failed, amendment_pending branches). Package bookings run a saga: reserve all items, confirm all or compensate (cancel the confirmed ones) on partial failure, with manual-intervention queues in the back office for the cases automation can't safely unwind — supplier no-answer, cancel-fee conflicts. Every transition posts ledger entries and emits webhooks/notifications.

5.5 Ledger, credit & payments

  • Credit control (B2B): agencies book against a credit limit or prepaid deposit; the reserve step places a hold, confirmation converts it to a receivable. Statements and aging reports in the back office.
  • Payments (B2C + agency top-ups): gateway abstraction with a Saudi-first implementation — Moyasar or HyperPay for mada, Visa/MC, Apple Pay. Card data never touches the platform (hosted fields/redirect), keeping PCI scope at SAQ-A.
  • Refunds flow through the same ledger with supplier-refund tracking, because supplier refunds arriving weeks late is the operational norm.

5.6 Documents & fiscal

Bilingual (Arabic/English) PDF generation for vouchers, itineraries, invoices, statements. Saudi tenants get ZATCA Phase-2 e-invoicing: XML invoice generation (UBL), cryptographic stamping, clearance/reporting API integration, QR codes on every invoice (§7).

5.7 Internal Dashboard & apps

Every tenant's staff work in one Internal Dashboard: a core workspace plus whichever apps the tenant has installed. The core workspace covers the bookings queue (with manual-intervention states), a search/book console for phone-in business, and Settings — fully self-service tenant configuration: supplier credentials (their own TBO/RateHawk/Hotelbeds accounts per §6), sub-tenant management entry points, markup rules, staff users & roles, branding, payment-gateway credentials, fiscal identity (VAT no., ZATCA onboarding). Each app is a NestJS module + a dashboard section + an external portal where applicable — and a separately priced SKU.

  • B2B app: the flagship. Staff side: trade-partner (agency) management, credit terms, markup profiles, statements. Portal side: sub-agents get fast streaming search, multi-room/multi-pax, quote baskets (offer PDF before booking), amendments/cancellation with fee preview, credit dashboard, sub-user management. Arabic-first RTL with English mirror.
  • Corporate app: staff side: corporate sub-tenant onboarding, travel policies, approval chains, account billing terms, cost centers, travel-spend reporting. Portal side: employees self-book within policy; out-of-policy requests route to approvers; arrangers book on behalf of travelers.
  • Accounting & Finance app: the ledger's face — receivables/payables, aging, statements, invoices and credit notes (ZATCA-cleared for Saudi tenants), VAT reports, supplier reconciliation. Crucially, it syncs with the finance systems tenants already run: a TRAACS connector first (the GCC agency standard — booking, invoice, and receipt records pushed automatically so settlement happens in the tenant's own books), plus generic journal/CSV export and webhooks for QuickBooks, Zoho Books, and ERPs. Jenova's ledger is the operational source of truth; the tenant's accounting system stays the fiscal one.
  • API Access app: key issuance per partner, per-key rate limits and usage metering, webhook subscriptions, published OpenAPI docs. The versioned REST surface mirrors the internal service contracts (/search, /check, /book…), which doubles as the platform's own contract documentation.
  • B2C Storefront app: theming (logo, colors, custom domain), destination content pages with SEO rendering, promotions; the consumer site itself runs guest checkout with gateway payment and an account area.
  • CRM app: customers and leads, quote pipeline (a quote basket becomes a CRM opportunity), follow-up tasks and reminders, campaign lists, customer travel history. Its edge over generic CRMs: every record links to real bookings, spend, and documents already in the system.
  • Omnichannel Support Desk app: one inbox for WhatsApp Business, email, and portal chat; conversations convert to tickets attached to a booking (amendment, refund, complaint) with SLA timers; canned bilingual replies; ticket events drive the same booking state machines staff use in the core workspace — a refund agreed in a ticket is executed, not re-typed.
  • Contracting app (own inventory): the tenant loads its directly negotiated hotel contracts — seasons, rate plans, allotments, release periods, stop-sales, free-night offers. Own contracts enter the same search fan-out as supplier APIs (the internal contract store is just another adapter), so agents see contracted and aggregator rates side by side. The deepest app in the catalog and the biggest revenue driver for DMC-type tenants.

The app framework is the product strategy: every app is expansion revenue on the installed base without touching the engine, and future candidates (Umrah operations, HR/duty travel, insurance) follow the same pattern.

5.8 Platform Admin console — Jenova's control plane

A separate application (separate deployment, separate auth realm, hardware-key 2FA) for Jenova staff — initially just you. It sits above tenancy: where tenant staff see their own world, Platform Admin sees and controls all of them. Everything it does is written to the same append-only audit log.

  • Tenant lifecycle: provision, configure, suspend, or offboard tenants; assign plans and per-app pricing; set usage limits (searches/day, bookings/month, API rate tiers); manage custom domains and branding approvals.
  • App & module control: the entitlement switchboard — enable/disable any app for any tenant, stage rollouts of new app versions behind feature flags, per-tenant configuration overrides, and kill switches: instantly disable a misbehaving supplier adapter, app, or tenant platform-wide without a deploy.
  • Full hierarchy visibility: drill from tenant → agencies and corporate sub-tenants → users → bookings, for support and dispute resolution. Includes audited impersonation: open any tenant's dashboard or portal as any of their users, with a banner shown, an audit entry written, and financial actions blocked while impersonating.
  • Supplier catalog: register adapters, track certification status per supplier, flip sandbox/production per tenant account, and watch per-supplier health boards (latency, error rate, look-to-book) with the ability to degrade or disable a supplier globally.
  • Platform billing: metering of every tenant's SaaS subscription, installed apps, and per-booking fees; invoice generation to tenants (ZATCA-compliant, since Jenova itself is a Saudi seller); dunning and suspension rules.
  • Cross-tenant operations: global booking-failure and manual-intervention queues, background-job monitor, webhook delivery logs, search across all tenants' bookings by reference/traveller/PNR.
  • Compliance & security: audit-log search across the platform, PDPL data-subject request tooling (export/erase a traveller's PII), user lockout, session revocation, and platform-wide announcements/maintenance banners.

Build note: Platform Admin grows with the platform — every milestone that adds a capability adds its admin surface in the same milestone (M2 tenants + entitlements, M3 supplier health, M4 billing, M5 ops queues), so there is never a feature you can sell but not operate.

5.9 Extensibility — per-tenant and per-sub-tenant customization

Tenants and their corporate/agency sub-tenants will demand integrations with the systems they already run — CRM, ERP, finance, HRM. The rule that keeps this survivable for one codebase: customization is configuration and connectors, never per-customer code forks. Four layers, each scoped to tenant or individual sub-tenant:

  • Custom fields: typed extra fields on bookings, travelers, and invoices (e.g. a corporate's employee ID, project code, HRM cost object), definable per sub-tenant, shown in its portal and carried through documents, exports, and every integration payload.
  • Events & webhooks: every business event (booking confirmed, invoice issued, refund posted, approval granted) publishable to per-sub-tenant webhook endpoints with signing, retries, and delivery logs — the universal integration primitive for anything with an inbound API.
  • Connector catalog: maintained connectors with per-sub-tenant credentials and field mappings — TRAACS first (§5.7), then generic accounting (QuickBooks/Zoho/ERP journal push), HRM sync (employee roster in → traveler profiles and cost centers, so a corporate's Data Vault and portal always match its HR system), and CRM sync. Mappings are configured in the dashboard, not coded.
  • Data Vault + Partner API: for anything the catalog doesn't cover, the sub-tenant's synced database (§3) and scoped API credentials let their IT or a hired integrator build against their own data without touching Jenova's core.

Commercially: connectors and custom integration work are a paid professional-services line on top of app subscriptions — the same model Odoo runs. Requests that recur across customers graduate into the catalog.

Supplier integration roadmap

Jenova never holds supplier credit

Jenova is a technology partner to suppliers, not a buyer. Aggregators grant technology partners free sandbox credentials to build and certify an integration — no deposits, no credit line, no commercial bookings on Jenova's account. Each tenant brings its own supplier contract (its own credit terms, deposits, negotiated nets) and plugs its production credentials into its SupplierAccount. Money and liability flow between the tenant and the supplier; Jenova earns SaaS + per-booking fees. Bonus: certified platforms get listed by suppliers, which becomes a customer-acquisition channel.

Suppliers below are chosen for GCC content strength, sandbox quality, and certification friction — the order will be finalized against the list of supplier test credentials already in hand, which are used for live-sandbox development from M1. Production certification per supplier is still a formal step, so technology-partner paperwork starts in month 1 in parallel with the code.

07

Saudi / GCC compliance layer

This is Jenova's moat as much as a checklist — incumbents treat all of it as professional-services work.

  • Arabic & RTL as the primary locale. Both portals and all documents are designed RTL-first with an English LTR mirror; i18n keys from the first component. Hijri dates displayed alongside Gregorian where users expect them (Umrah-adjacent bookings); storage is always Gregorian UTC.
  • ZATCA e-invoicing (Fatoora, Phase 2). Saudi tenants must clear/report invoices with ZATCA: UBL 2.1 XML, XAdES signing with device credentials per tenant, B2B clearance and B2C reporting flows, QR (TLV) codes. Build as an isolated fiscal-sa module behind an interface so other GCC fiscal regimes slot in later. Onboarding a tenant includes a ZATCA device-registration step.
  • VAT 15% with correct treatment per case (domestic vs. international transport, agent-vs-merchant model per tenant configuration). The ledger carries VAT accounts natively.
  • PDPL (Saudi data protection). Traveller PII minimized, encrypted at rest, retention policies per record class, data-processing terms in tenant contracts. Host in-region: AWS Bahrain (me-south-1) or a Saudi region (AWS/GCP/Oracle in KSA) — decide with first enterprise tenant; PDPL favors in-Kingdom for government-adjacent buyers.
  • Payments: mada is non-negotiable for Saudi B2C conversion; Apple Pay close behind. Moyasar/HyperPay cover both. Multi-currency display with SAR settlement default.
  • Nationality-based rates: hotel APIs return different rates by guest nationality/residency — a first-class search parameter, defaulted per agency, never hidden.
  • Umrah readiness: Makkah/Madinah hotel packaging with ground transport is a huge regional segment. The launch platform needs nothing special beyond good Makkah content; the package saga and Contracting app are the foundation a future Umrah-operations app builds on.

Working rules

  • Contracts before code. Every module starts as a typed interface + test suite agreed in a planning session; agents implement to the contract. The supplier-sdk contract tests are the canonical example: a new adapter is "done" when the shared suite passes against recorded sandbox fixtures.
  • One agent, one package. Parallel agent sessions map to package boundaries (a supplier adapter, one dashboard app, the pricing engine). The dependency-lint rule stops boundary violations mechanically rather than by review vigilance.
  • Sandbox credentials are the keystone. Real supplier test credentials are wired in from M1, so every downstream feature — apps, sagas, ledger, e2e suites — develops and demos against real supplier flows. The record-and-replay harness captures that live traffic so agent-written tests stay deterministic in CI without any fabricated data.
  • You own the irreducibly human work: supplier commercial agreements and certification sign-off, ZATCA/PSP onboarding, tenant sales, production access and secrets, and final review of anything touching money movement or PII.
  • Review budget is the real bottleneck. Plan for roughly 2–3 substantial agent workstreams in flight at once; more than that and unreviewed merges accumulate risk in exactly the modules (ledger, booking sagas) that can't absorb it.

Milestones

Months are calendar months of focused solo-plus-agents work. Every milestone ends demo-able; from M5 the platform is commercially usable and each later milestone widens the catalog. Dates slip on external dependencies (certifications, ZATCA, PSP onboarding) before they slip on code — start all of those in M1.

M0wk 1–2

Foundations

Monorepo, CI, CLAUDE.md conventions, domain package (money, tenancy, state-machine primitives), control-plane + tenant DB schemas v1 with per-tenant database provisioning and the fan-out migration runner, auth skeleton, deploy pipeline to a staging VM.

Done when: an agent can clone, test, and ship a reviewed PR to staging unaided.

M1mo 1

Engine spine on live supplier sandbox

Supplier-sdk contracts; first hotel adapter wired to a real supplier sandbox using the test credentials in hand; record-and-replay harness capturing that live traffic for CI; search fan-out with streaming; pricing engine with rule resolution; hotel booking state machine; offer cache with signed prices.

Done when: API can search → check → book → cancel a real sandbox hotel end-to-end with correct ledger postings, and the contract suite passes in CI against recorded traffic.

M2mo 2

First real supplier + B2B app alpha

TBO hotel adapter certified against sandbox; Internal Dashboard shell with app framework (entitlements, navigation); B2B app: agency management + Agent Portal with login, streaming hotel search, book, booking list, voucher PDF. Arabic/English from the first screen.

Done when: a real TBO sandbox hotel is booked and cancelled from the portal in both languages.

M3mo 3

Money is real

RateHawk adapter + hotel mapping service integration (dedup live); credit limits and agency statements; markup management UI; Moyasar/HyperPay integration for agency top-ups; back-office booking queue with manual-intervention states.

Done when: two-supplier deduped search books against agency credit, and finance reports reconcile to the ledger.

M4mo 4

App suite live (hotels)

Accounting & Finance app UI over the ledger; B2C Storefront app with tenant theming, guest checkout, mada/Apple Pay; API Access app with keys, metering, OpenAPI docs; tenant provisioning + app entitlements in platform admin; ZATCA invoice clearance for Saudi tenants.

Done when: a new tenant is provisioned in under a day, installs its apps itself, and sells the same hotel through Agent Portal, storefront, and API with cleared invoices.

M5mo 5

Pilot launch — hotels GA

Hardening: load tests, supplier failover drills, observability dashboards, backup/restore drills, pen-test pass on auth and payment flows. Onboard 1–3 pilot tenants at founder pricing.

Done when: a pilot tenant's agents book real, paid hotel stays in production. Revenue starts here.

M6–7mo 6–7

Corporate app

Corporate sub-tenant model; travel policies and approval chains; Corporate Portal (employee self-booking within policy, arranger booking, approver flow); account billing + cost centers wired into the ledger; travel-spend reports.

Done when: a pilot tenant onboards a real corporate client whose employee's out-of-policy hotel booking routes to an approver and bills to account.

M8–9mo 8–9

Transfers & activities

Ground adapter contract; Hotelbeds transfers + activities adapters; both products across every app and portal; multi-item bookings (hotel + transfer) exercising the saga with compensation paths.

Done when: a hotel+transfer booking survives a forced partial failure by compensating cleanly, in production.

M10–12mo 10–12

Flights via consolidator

Flight adapter (Mystifly/TBO Air): search, fare rules, PNR, ticketing, void/refund states; seat/baggage basics; flight UX in every portal, with corporate policy rules (cabin class caps) applied; e-ticket documents; airline-refund tracking in the ledger. The commercial agreement must be signed by ~M7.

Done when: a ticketed flight books, voids, and refunds correctly end-to-end in production.

M13mo 13

Dynamic packages — full v1

Package composer (flight + hotel + transfer) with combined pricing and one checkout; package saga across three verticals; package documents. This completes the product-vertical surface.

Done when: a bundled Jeddah package (flight + Makkah hotel + transfer) sells through the Agent Portal and B2C.

M14mo 14

Commercial GA

Public pricing/onboarding, docs portal for the Partner API, SLA monitoring, self-service app installation end-to-end. The booking platform is complete; the remaining catalog apps continue below while GA tenants onboard.

Done when: tenants onboard without your personal involvement in every step.

M15–16mo 15–16

CRM + Omnichannel Support Desk apps

CRM: customer/lead records, quote pipeline fed by quote baskets, tasks, travel history. Support Desk: WhatsApp Business + email + chat inbox, tickets bound to bookings, SLA timers, ticket-driven amendments/refunds through the booking state machines.

Done when: a WhatsApp refund request becomes a ticket, an approval, and an executed refund without leaving the dashboard.

M17–20mo 17–20

Contracting app — full catalog

Own-contract store: seasons, rate plans, allotments, release periods, stop-sales, offers; exposed to search as an internal supplier adapter so contracted rates compete with aggregator rates in the same results. Completes the eight-app catalog.

M21+post-GA

Isolation tiers & deep extensibility

Dedicated-database tier with automated migration fan-out; sub-tenant Data Vault sync (change-data-capture to customer-hosted databases, cloud or on-prem); custom-fields and connector-catalog framework beyond the TRAACS connector (accounting, HRM, CRM); first private/on-premise tenant deployment with licensed update channel. Sequenced by which enterprise deal demands which piece first.

Done when: a corporate sub-tenant's on-prem Data Vault stays in sync within a minute, and one enterprise tenant runs the stack in its own cloud on the standard update channel.
